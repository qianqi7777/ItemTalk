# V1 备份与失败告警实施方案

当前交付范围是本地代码、Mock COS/测试数据库验证、模板和方案。真实 COS 与邮件通知未验收，生产定时任务、告警规则均未启用。不得将 Mock 结果填写为真实服务验收。本文与代码不会创建云端告警规则，也不会修改服务器。

## 地域、配置和权限

2026-10-14 通过实例内只读元数据查询，服务器为 `ap-beijing`；用户指定备份桶 `itemtalk-backup-1314964135` 位于 `ap-nanjing`，地域不同。查询方法依据[腾讯云实例元数据文档](https://cloud.tencent.com/document/product/213/4934)。真实验收时仍需核对桶实际地域及私有权限，不能仅凭模板认定已完成云配置。

应用照片/说明书继续使用 `COS_BUCKET`。`BACKUP_COS_SECRET_ID/KEY` 仅用于读取应用资产，可配置独立只读凭据。数据库异地备份使用独立 `DB_BACKUP_COS_*`，不回退到应用桶/应用凭据。`infra/backup.env.example` 是服务器 `/opt/itemtalk/.env.backup` 的模板，真实文件由 `ubuntu` 持有、权限 `0600`，不得提交。Compose ≥2.24 读取该受限文件；缺文件时其他服务仍可解析配置，备份任务必须失败关闭。数据库管理员凭据仍来自受限 `.env.production`，不向 API/Worker 传递。

备份上传账号的最小权限为指定桶的版本/ACL/策略只读检查，以及 `itemtalk/postgresql/*` 下 `PutObject`、`GetObject`。不授予 `DeleteObject`、桶配置写入、生命周期修改或应用桶写入权限。私有 ACL、无扩大访问的桶策略必须核验；当前禁止覆盖协议要求目标桶未启用/暂停版本控制，有其他需求应先审核方案。SDK/API 直接访问，不挂载 COS。

## 每日备份与保留

`app.backup_jobs daily` 复用 `app.restore_check`：一致性只读数据库快照导出、只读采集数据库登记的 COS 资产、核对可用资产大小与 SHA-256，并重新检查原对象未被改写。生成数据库 `.dump`、资产归档、结构/内容/权限清单、SHA-256 清单四个文件。在线快照不包含快照之后的普通写入，不代替迁移前的停写备份。

每日阶段检查 dump 目录，但不声称已经恢复。四个文件逐个上传到唯一日期/UUID 前缀，私有写入并禁止同名覆盖；随后逐个从 COS 流式读回核对大小和 SHA-256。每文件上限 2 GiB，超过上限失败并保留本地文件，应在扩容时审核流式/分段上传方案。只有全部核验成功才生成 `completed-*.json`，状态 `uploaded-verified`、`restoreVerified=false`。第一次上传前先写 `attempt-*.json`，半途失败不会丢失远端前缀记录，不能标记完成。

本地保留最近 7 天的**已上传并核验**备份。清理前核验该完成记录的全部固定文件、哈希及普通文件类型，禁止链接、路径跳转或清理未知历史备份。只删除本地四文件及对应完成记录；小型尝试/演练/告警记录另行管理。上传失败的唯一副本、未知旧维护备份不自动删除，应由运维在安全保全后处理，并监控磁盘空间。COS 历史对象和不完整上传前缀一律保留，脚本没有删除接口；本方案不配置过期生命周期。

每日 timer 方案为东八区 03:00。`BACKUP_JOBS_ENABLED=false` 默认关闭；未审核启用前不安装/启动生产定时器。运行采用共享部署锁及独占备份锁，不自动重建、启动或暂停生产服务。

## 每周隔离恢复

`app.backup_jobs weekly` 从受限本地完成记录选择最近成功备份，核对配置的桶/地域一致；从 COS **重新下载**四文件到自身临时目录，先检查全部哈希及校验清单。随后在新建的 `itemtalk_restore_<随机标识>` 数据库执行真实 `pg_restore`，比较表内容摘要、结构、扩展、约束、RLS、权限、函数与触发器，恢复资产至独立本地临时目录并核对数据库引用。

生产数据库不作为恢复目标。只清理本轮创建成功的临时数据库/临时目录；创建失败时不删已有数据库。失败不会生成 `weekly-*.json` 成功记录。恢复所需角色和扩展必须已在验证环境具备；数据库 dump 不包含全局角色，不能代替维护窗口的角色/受限配置备份。timer 方案为周日东八区 04:00，与每日任务共用锁。

## 告警事件与腾讯云邮件方案

本地事件记录 `kind`、`eventId`、时间、尝试次数及受控状态，不写用户数据、邮箱、凭据、SDK URL 或原始异常。备份/恢复 CLI 失败会产生事件；systemd `OnFailure` 的独立宿主 Python 入口在 Docker/数据库不可用时也能落盘，不依赖 API 镜像。事件落盘失败必须让服务失败并留 systemd 日志，不能吞掉。

`app.ops_alerts` 默认保持渠道关闭。待发送事件不消耗次数；启用后的渠道适配器无有效提交回执、抛异常或返回失败时，保留 `retry-wait` 和受控错误码。指数退避从 60 秒起，最多 5 次；耗尽后 `exhausted` 仍保留供人工处理。测试中的 Mock 仅验证这套流程。当前真实渠道适配器未连接，设置模板开关本身不会发通知。

有效提交回执只代表 `submitted`，不代表邮件已经送达；只有另外取得送达确认才允许 `notificationVerified=true`。渠道关闭、缺适配器、失败、排队均不能标为发送成功。调用投递器必须串行执行；云端告警按事件类型/服务器聚合并限频，避免 CLI 与 systemd 的重复失败事件引起邮件轰炸。

腾讯云实施采用可观测平台监控服务器/HTTPS，配合 CLS 日志告警收集 `/opt/itemtalk/backups/alerts/event-*.json` 的固定 JSON 字段，对 `daily-failed`、`weekly-failed`、`health-failed` 设置邮件通知和聚合。先建立专用日志主题/采集配置及通知模板，并在云控制台验证联系人邮件；配置项在 `backup.env.example` 留空，`OPS_ALERTS_ENABLED=false`。CLS 采集成功仍只证明日志接收，通知回执/邮件收件确认须单独记录，不能当作本地 sender 的成功回执。无需部署 Prometheus/Grafana。

当前 API 文档有旧接口下线/移除记录，不能直接照旧教程接 `PutMonitorData` 或 `SendCustomAlarmMsg`。实施时使用当前支持的云控制台日志告警与通知模板：[监控更新记录](https://cloud.tencent.com/document/product/248/30349)、[CLS 通知渠道组](https://cloud.tencent.com/document/product/614/59661)。还需监控每日成功备份超过 26 小时未出现、每周演练超过 8 天未成功、磁盘空间不足及采集/通知渠道异常；仅监测脚本主动失败不够覆盖未运行/主机故障。

GitHub Actions 采用 GitHub 原生工作流失败通知；由仓库参与者检查个人通知设置并完成一次工作流失败通知验收。代码不能证明账户已启用邮件通知，也不新增邮件密钥。

## 待确认后的真实验收入口

下面仅给出审核用入口，当前不执行。在固定版本运维容器中加载受限配置后：

```text
python -m app.backup_jobs daily --real-cos --pg-bin /usr/lib/postgresql/16/bin --output-directory /backups
python -m app.backup_jobs weekly --real-cos --pg-bin /usr/lib/postgresql/16/bin --output-directory /backups
python -m app.ops_alerts --directory /backups/alerts --emit notification-test
```

前两个入口分别验证真实上传/下载/校验与隔离恢复；第三个只生成待发送事件，**不会发送邮件**。真实告警须在联系人、采集和规则配置确认后，走已配置云渠道发送并记录至少一次实际收件确认。不要为测试覆盖生产数据；使用专门验收数据库/数据，真实服务测试及生产改变均须用户确认。

上线审核包应包含固定镜像摘要、当前服务/备份状态、预留空间、云端最小权限与桶地域证据、真实上传/恢复报告、至少一次真实通知证据、安装的 unit/timer 和失败回滚步骤。回滚先停止新增 timer/告警规则、保持历史 COS 与本地备份，再恢复原配置/unit；数据库不因撤回定时任务而降级或覆盖。实际安装/启用命令须在审核包确认后执行。

四种状态分别记录：**本地实现完成**、**本地测试通过**、**真实服务待验收**、**生产未启用**。真实COS上传、文件完整性校验、独立数据库恢复及至少一次真实告警通知全部通过前，生产备份和失败告警不得标为“已上线”或“验收完成”。
