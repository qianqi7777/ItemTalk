# 备份与告警

[← 项目首页](../README.md) · [发布与维护](MAINTENANCE.md) · [运行管理](V2_RUNTIME.md) · [配置模板](backup.env.example)

本文描述可选的 COS 定时备份、隔离恢复和失败通知机制。服务器试用可继续使用本地资产与人工配对恢复；这些可选任务默认关闭，不因应用升级而自动安装。

> **分别记录实现、测试、真实服务验收和实际启用状态。** Mock 通过、镜像可拉取、日志被采集，都不能当作备份已恢复或邮件已送达。

## 能力与默认状态

| 能力            | 实现行为                                   | 启用要求                                       |
| --------------- | ------------------------------------------ | ---------------------------------------------- |
| 人工配对备份    | 停写、保存 DB/资产、实际隔离恢复           | 每次维护核对恢复点                             |
| 每日 COS 备份   | 一致性快照、对象归档、上传并逐文件读回校验 | `BACKUP_JOBS_ENABLED=true`，独立凭据与任务验收 |
| 每周恢复        | 从 COS 重下已完成备份，恢复新库及临时目录  | 真实下载、结构/内容/文件验证通过               |
| 本地失败事件    | 受控 JSON，重试状态和失败记录              | 受限且可写的事件目录                           |
| 云端通知 / SMTP | 云规则或独立邮件适配路径                   | 渠道、联系人、提交和收件证据分别核对           |

开关默认 `BACKUP_JOBS_ENABLED=false`、`OPS_ALERTS_ENABLED=false`。备份任务不调用模型，不会自动启动、重建或暂停生产 API/Worker/数据库。

## 配置与最小权限

| 配置                       | 用途                         | 边界                                              |
| -------------------------- | ---------------------------- | ------------------------------------------------- |
| `COS_BUCKET` 等应用配置    | 应用资产所在桶               | 不作为数据库备份桶的自动回退                      |
| `BACKUP_COS_SECRET_ID/KEY` | 只读应用资产                 | 可独立只读授权，不允许应用桶写入                  |
| `DB_BACKUP_COS_*`          | 独立数据库备份桶、地域、凭据 | 与应用桶/凭据分开，目标地域独立核对               |
| `.env.production`          | 受限数据库运维配置           | 管理员连接不传给 API/Worker                       |
| `.env.backup`              | 受限备份与通知配置           | 模板见 [`backup.env.example`](backup.env.example) |

服务器文件由部署用户持有，权限 `0600`；本地使用等价专属 ACL。Compose 2.24+ 支持可选环境文件；缺少备份配置时其他服务可以解析，但备份任务必须失败关闭。

上传账号只需指定桶的版本/ACL/策略只读检查，以及 `itemtalk/postgresql/*` 前缀下 `PutObject/GetObject`。不授予 `DeleteObject`、桶配置写入、生命周期修改或对象 ACL 更改。参考[最小权限策略模板](cos-backup-policy.example.json)，实际桶名、地域与资源范围须核对。

桶须私有、无扩大读取的策略。当前禁止覆盖协议要求未启用/暂停版本控制；不同版本保留需求需另行设计，不能认为版本桶同样提供禁止覆盖语义。使用 SDK/API，不挂载 COS。

## 每日备份

`app.backup_jobs daily` 复用 `app.restore_check` 的一致性快照与只读资产采集，生成四类文件：

| 产物        | 内容                                   |
| ----------- | -------------------------------------- |
| 数据库 dump | PostgreSQL custom 格式快照             |
| 资产归档    | 数据库登记的当前 COS 对象              |
| 清单        | 结构、表内容、权限、对象大小与 SHA-256 |
| 校验文件    | 固定产物的 SHA-256                     |

处理顺序为：

```text
导出快照与只读对象 → 检查对象未变化 → 写入 attempt 记录
        ↓
上传唯一日期 / UUID 前缀 → 逐文件读回校验大小与 SHA-256
        ↓
全部通过 → completed 记录：uploaded-verified
```

每日阶段检查 dump 目录，**不声称已实际恢复**，结果为 `restoreVerified=false`。每文件上限 2 GiB，超限失败并保留本地文件；扩容时另审流式或分段方案。失败前缀保存在 `attempt-*.json`，不生成成功完成记录。

在线快照不包含快照之后的写入；对象缺失、哈希不符或被改写会失败。它不能替代维护发布前的停写备份。

### 保留与调度

- 本地只自动清理超过 7 天、已经上传核验的自身备份；先检查完成记录、固定文件、普通文件类型和全部哈希。
- 上传失败的唯一副本、未知旧维护备份、链接或越界路径不自动删除。
- COS 历史对象与不完整前缀保留；脚本没有远端删除接口，也不配置过期生命周期。
- 默认方案为东八区每日 03:00；timer 只有审核启用后才安装。共享部署锁与独占备份锁避免重叠。

## 每周隔离恢复

`app.backup_jobs weekly` 从受限完成记录选择最近成功备份，核对桶与地域，从 COS **重新下载**四文件，先检查哈希与清单，再执行真实 `pg_restore`。

恢复目标是本轮新建的 `itemtalk_restore_<随机标识>` 数据库及独立本地目录，不是生产库。验证内容包括表摘要、结构、扩展、约束、索引、RLS、所有权/权限、函数、触发器和资产字节及数据库引用。

只清理本轮成功创建的目标；创建失败不删除已有数据库。失败不生成 `weekly-*.json` 成功记录。需预置同名角色和扩展；dump 不包含全局角色，不能替代原配置与角色恢复依据。默认方案为周日东八区 04:00，与每日任务共用锁。

COS 资产恢复到本地临时目录，不等于目标 COS 桶回写成功；对象历史和未登记孤儿对象也不在该恢复范围。

## 失败事件与通知

事件只记录 `kind`、`eventId`、时间、尝试次数和受控状态，不写用户内容、邮箱、凭据、SDK URL 或原始异常。CLI 失败和 systemd `OnFailure` 都可落盘；宿主入口不依赖 API 镜像，Docker/数据库故障时仍可记录。落盘失败必须保留服务失败及 systemd 日志。

| 状态                        | 意义                         |
| --------------------------- | ---------------------------- |
| 待发送 / 渠道关闭           | 事件保留，未实际通知         |
| `retry-wait`                | 提交失败，按退避等待重试     |
| `exhausted`                 | 达到尝试上限，保留供人工处理 |
| `submitted`                 | 获有效提交回执，不等于收件   |
| `notificationVerified=true` | 另有真实送达确认             |

`app.ops_alerts` 默认关闭。适配器缺失或提交失败不能标成功；指数退避从 60 秒起，最多 5 次，投递器串行运行。仅填写云变量或切换模板开关不会自动创建规则或发送邮件。

可在云平台配置服务器/HTTPS 监测与 CLS 日志采集，收集 `/opt/itemtalk/backups/alerts/event-*.json` 的固定字段，对 `daily-failed`、`weekly-failed`、`health-failed` 聚合通知。具体 API、采集规则与通知模板以实施时供应商文档为准，联系人和收件确认单独验收。

除主动失败外，还需监测：每日成功备份超过 26 小时未出现、每周演练超过 8 天未成功、磁盘不足、主机故障及采集/通知异常。GitHub 工作流失败通知使用参与者的 GitHub 通知设置，不由仓库代码保证邮件已启用。

## 验收入口

在固定版本独立备份容器内加载受限配置后，入口为：

```text
python -m app.backup_jobs daily --real-cos --pg-bin /usr/lib/postgresql/16/bin --output-directory /backups
python -m app.backup_jobs weekly --real-cos --pg-bin /usr/lib/postgresql/16/bin --output-directory /backups
python -m app.ops_alerts --directory /backups/alerts --emit notification-test
```

前两项读取数据库与源资产并访问真实 COS，不能当作仅合成小文件的供应商预检。第三项只生成事件，**不会发送邮件**。本地可用重复 `--env-file` 加载独立验收配置，避免操作生产数据。

可选 SMTP 的 `python -m app.ops_mail --env-file <受限文件>` 默认仅检查配置。单次真实测试还需 `--send-test`、`--real-email`、独立测试开关和新的受限 `--report`；SMTP 接受仍不代表送达。配置项见[模板](backup.env.example)。

## 启用与撤回

启用前按[维护手册](MAINTENANCE.md)核对：

- [ ] 固定镜像摘要、PostgreSQL 客户端版本与受限运维 UID/GID。
- [ ] `/opt/itemtalk/backups` 所有权、磁盘和隔离恢复空间。
- [ ] 当前服务/备份状态、桶地域和最小权限证据。
- [ ] 真实上传、读回哈希、隔离恢复及相应通知验证。
- [ ] unit/timer、锁、监测未运行的规则及回退步骤。

独立 `backup` 容器使用只读根文件系统与专用目录，通过 `--no-deps` 运行，不重启已有服务。实际安装和云规则变更按已确认范围执行。

撤回时先停止新增 timer/告警规则，保留历史 COS 与本地备份，再恢复原配置/unit。撤回定时任务不需要降级数据库或覆盖业务库。配置完成、真实服务验收和实际启用应在受限运维记录中分别填写。
