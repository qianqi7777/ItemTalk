## 理解发布流水线

| 阶段         | 工作流                                                            | 证明了什么                                                  |
| ------------ | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| 测试         | [CI](../.github/workflows/ci.yml)                                 | 前端、后端/数据库、容器和浏览器检查通过                     |
| 自动部署路径 | [Deploy](../.github/workflows/deploy.yml)                         | 只有 `expand-only` 才继续构建与连接服务器；当前维护版本跳过 |
| 维护打包     | [Maintenance images](../.github/workflows/maintenance-images.yml) | 发布固定摘要镜像与配置包，不含 SSH 部署步骤                 |
| 实际上线     | 经审核的维护操作                                                  | 备份恢复、配置核对、迁移、健康与业务验收                    |

主分支成功 push CI 可触发后续工作流；手动运行须提供同一主分支完整 40 位 SHA，并验证该 SHA 的成功 CI。工作流成功、镜像推送成功和服务器已切换是不同结论。

## 发布前准备

- [ ] 确认最终完整 SHA、成功 CI、迁移目标及兼容类型。
- [ ] 核对旧发布、当前 schema、运行服务、数据库/资产大小和磁盘余量。
- [ ] 复核新旧有效配置差异，保留现有密钥、加密主密钥、四类模型、额度和存储路径。
- [ ] 明确 API、Worker、迁移与管理员角色，运行身份无超级用户、BYPASSRLS 或对象所有权。
- [ ] 准备数据库、资产、原配置和角色权限恢复依据，明确保留位置与回退时间。
- [ ] 验证本次变更相关真实能力；单一设备、mock 或中断报告不代表全面质量验收。
- [ ] 形成具体服务器、停写范围、恢复点和回滚清单，按已授权范围执行维护。

API 使用 `itemtalk_app`，Worker 使用独立 `itemtalk_worker` 和密码，迁移使用对应迁移身份。不要输出完整 Compose 渲染结果、生产环境变量或私人内容。

共享服务器示例入口为 `/itemtalk/`：Caddy 仅环回 8400，前置 Nginx 剥离前缀并关闭 SSE 缓冲。前端 base、API URL 和 Cookie Path 必须一致。独立 HTTPS Compose 仅用于独占 80/443 的环境；不要把开发 Compose 暴露到公网。

## 固定发布产物

维护工作流构建并拉取 API、前端、数据库和独立备份镜像，核对源码 SHA。备份镜像基于同次 API 摘要，另装 PostgreSQL 16 客户端，验证受限 UID 的离线入口。

| 文件                  | 用途                                                      |
| --------------------- | --------------------------------------------------------- |
| `release.json`        | 源 SHA、成功 CI、目标迁移 revision、兼容类型和镜像摘要    |
| `image-overrides.env` | `API_IMAGE/DB_IMAGE/FRONTEND_IMAGE/BACKUP_IMAGE` 摘要引用 |
| `release-config.tar`  | 该提交跟踪的 Compose、SQL 与 infra 文件                   |
| `release.sha256`      | 固定产物校验和                                            |

下载后逐项核对校验和、SHA、CI、revision 和摘要。目标 revision 来自镜像的离线 `alembic heads`，不代表服务器当前 revision。产物保留 30 天，上线前保存受限审核副本。

将确认的 `image-overrides.env` 保存为本次发布目录 `.env.image_tag`，与服务器受限 `.env.production` 分开加载。API/Worker/migration 共用 `API_IMAGE`，不要把旧 SHA 标签当固定摘要。备份工具是独立运维容器，不把管理员连接传给 API/Worker。

## 停写与配对恢复

1. 取得部署互斥锁，记录当前发布与摘要；不要与其他部署或备份重叠。
2. 停止 API、Worker、后台清理与其他写入口，核对实际状态。仅打开“后台暂停”不算停写。
3. 保存 PostgreSQL custom dump、配对资产归档、结构/内容摘要清单和校验和，同时保全受限配置及角色权限。
4. 在本次新建的隔离数据库和空目录中**实际恢复**。核对全部表内容、扩展、约束、索引定义、RLS、所有权/ACL、守卫函数和触发器；文件核对大小与 SHA-256。
5. 恢复验证失败则停止继续发布，保留原数据库、资产与配置；不能把 `pg_restore --list` 或归档目录列表视为实际恢复。

从后端环境运行本地资产配对验证的通用入口如下，尖括号需替换为明确路径。此操作需建库/恢复权限、匹配客户端与足够容量：

```text
uv run python -m app.restore_check --assets-directory <资产根目录> --writers-paused --output-directory <资产目录外的受限备份目录>
```

Windows 可增加 `--pg-bin <PostgreSQL客户端目录>`。恢复工具只清理本轮成功创建的临时库和目录，保留备份；不要手动覆盖唯一恢复点。

## 迁移与启动

1. 用管理员预置 [`runtime-roles.sql`](runtime-roles.sql) 所需角色和授权；新库初始化与已有库权限迁移分开处理。
2. 保持停写，用迁移身份执行目标镜像的 `alembic upgrade head`，核对精确 revision，不自动 downgrade。
3. 使用固定摘要和已审核配置启动受限 API/Worker；默认保留既有数据库容器，数据库升级属于独立维护。
4. 检查健康与 `buildVersion`、镜像摘要、角色隔离、四类配置和额度计数。
5. 业务验收与健康一致后原子更新 `current`；保留原发布、原配置与恢复点。

需要从本地存储迁移 COS 时，先完成[存储迁移](#可选存储迁移与恢复)。只改 `STORAGE_BACKEND` 会让原有对象无法读取，不是迁移。

## 上线验收

- [ ] HTTPS、路由前缀、Cookie、认证、API 与 Worker 健康，`buildVersion` 等于目标 SHA。
- [ ] 静态资源正确，新旧 Worker 不同时写入；任务领取、续租、清理和 RLS 正常。
- [ ] 用本次专用数据或公开资料验证变更相关功能，避免读写其他用户内容。
- [ ] 涉及问答时分别检查官方、第三方和模型推测的依据与标识，来源撤销仍有效。
- [ ] 涉及模型时检查实际协议、快照、额度与超时，不把 mock 结果冒充真实调用。
- [ ] 核对原资产与配置、证书续期和空间；只检查实际已启用的告警/备份，不自行新增服务。
- [ ] 记录旧/新 SHA、schema、时间、备份位置、通过项和未覆盖范围。

## 失败与回滚

先判断数据库兼容性，再选择恢复方式：

| 情况                               | 处理                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| 新旧应用兼容现有 schema            | 停止新应用，恢复旧固定镜像及原配置，保留兼容 schema，不覆盖业务库 |
| 目标旧应用不支持新模型协议/快照    | 先按[运行管理](V2_RUNTIME.md#兼容回退)恢复兼容配置并处理任务      |
| 跨越不兼容 RLS、角色或 schema 边界 | 保持停写，按审核恢复点配对恢复数据库、资产、配置和权限            |
| 首次部署失败                       | 停止失败应用，按方案撤销新路由，保留诊断与恢复依据                |

回滚后核对旧 SHA、HTTPS、认证、资产、任务和角色，确认没有双 Worker。数据库恢复可能丢失恢复点之后的写入，须明确影响，不能代替可兼容的应用回退。原有 `deploy.sh` 仅处理其支持的兼容发布，不可替代维护流程。

## 可选存储迁移与恢复

### 本地文件迁移 COS

```text
uv run python -m app.storage_transfer --assets-directory <源资产目录> --writers-paused --report <新的受限报告文件>
```

默认只生成计划；验证恢复点和目标配置后，按已授权方案加 `--apply`。保持停写，逐文件校验大小与 SHA-256、保留原键、复用同内容目标、拒绝冲突覆盖。工具不改源库/文件或桶策略，旧文件和配置保留到回退期限结束。

目标需私有 ACL、无扩大读取权限的策略，以及符合禁止覆盖语义的版本控制状态；不能为测试关闭桶权限保护。未确认上传和清理对象也保留清单及签名到期依据。

### COS 配对恢复与供应商预检

`app.restore_check --cos-assets --writers-paused` 按数据库登记对象备份，不扫描共享桶或桶版本历史。实际恢复到新数据库和隔离本地目录，`assetRestoreTarget=local-isolated`；它不证明目标 COS 回写和新适配器读取已通过。

`app.cos_probe --real-cos --origin <前端Origin> --report <新的受限报告文件>` 仅测试本轮合成对象的私有访问、CORS、签名与字节回写，不改桶策略或访问业务数据库。退出后检查受限报告中的清理状态；它不能替代应用上传确认、越权和配对恢复验收。

在线 COS 备份可使用 `--online-immutable-assets`，恢复导出快照，检查对象大小/哈希与后续变化；不涵盖快照后的写入，不能代替迁移前停写恢复点。定时任务和告警需独立配置与验收，见[备份与告警](BACKUP_AND_ALERTS.md)。
